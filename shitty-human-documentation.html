Orientation

What it actually is

Shitty Human ("rate your day" — that's the literal <title>) is a daily mood-rating app: pick a number 1–10, add a note and up to three context tags, decide if it's private. On top of that single-player core it layers a genuinely full social product — username-based friend requests, real-time 1:1 chat with text/shared-day-cards/30-second voice notes, emoji reactions, a 13-item achievement system the app calls Citations, a head-to-head "Compare" view against one friend at a time, and a client-toggled Premium tier unlocked with redeem codes.

There is no backend. Every screen talks straight to Firebase from the browser — Firebase Authentication for accounts and Cloud Firestore for every piece of data, real-time listeners included. The firestore.rules file you provided isn't a nice-to-have here; it is the entire access-control layer for the app.

Note on scope — dayMarkers and groups

Your brief for this document listed dayMarkers and a groups collection (for group chat). I searched index.html for every .collection(…) call — there are 46 of them — and neither exists. Chat is 1:1 only, through friendships/{pairId}/messages; there's no group thread anywhere in the code, and the rules you pasted don't have a match /groups/{'{'}...{'}'} block either. I've documented the app as written above. If group chat or a separate day-marker log is on your roadmap, both would need new collections and new rules blocks — right now, writing to either would be silently rejected (Firestore denies by default when no rule matches a path).

Note — ratings.tags isn't shape-checked

The ratings rule validates rating, note, private, username, and updatedAt, but it doesn't call .keys().hasOnly([…]) the way the messages rule does — so tags, ratedAtHour, and createdAt pass through without a type or size check. Nobody can touch another user's rating either way (that's still gated by isSelf(...)), it's just a looser check than the rest of the schema if you're tightening things up later.

Data & auth

Authentication

There's no real email collected anywhere. Firebase's email/password provider needs something email-shaped, so the app manufactures one from the username:

usernameToEmail()index.html · line 1214
function usernameToEmail(username) { return username.trim().toLowerCase().replace(/[^a-z0-9_]/g,'') + '@dayvibe.local'; }

A username of jordan_k becomes the Firebase Auth identity jordan_k@dayvibe.local — a domain that doesn't need to resolve to anything, because Firebase Auth never actually sends mail through it. The regex strips anything outside a-z0-9_ after lowercasing, so it's tolerant of case but still guarantees a valid local-part.

Signup

Client-side validation first — username 3–15 chars matching ^[a-zA-Z0-9_]{3,15}$, password ≥ 6 characters, an avatar (philosopher) selected. Then it's a two-step write: create the Auth user, then create the Firestore profile. If the profile write throws, it deletes the just-created Auth user so you don't end up with an orphaned account that has no profile:

Login & logout

Login re-derives the same fake email and calls signInWithEmailAndPassword. Logout is a one-liner: auth.signOut(), after clearing in-memory friend/chat state via resetSocialState() so a second account signing in on the same tab doesn't inherit stale listeners.

Firebase's auth/* error codes are translated to plain copy by friendlyAuthError() — auth/email-already-in-use becomes "That username is taken," auth/wrong-password and auth/user-not-found both collapse to "Incorrect username or password" (so login never leaks which part was wrong).

Re-authentication for account deletion

The same fake-email trick is reused when a user deletes their account — firebase.auth.EmailAuthProvider.credential(usernameToEmail(currentProfile.username), password) rebuilds a credential to reauthenticate before Firebase will allow currentUser.delete().

Security rules

Because there's no backend, firestore.rules is the only thing stopping any signed-in user from reading or writing anyone else's data. It's organized as one helper block plus four match blocks that mirror the four collections above one-for-one.

⚠ The isPremium lock vs. the redeem button

This is the same issue flagged in Overview, in more detail. The users/{uid} update rule requires the new value of isPremium to equal the existing one:

users/{uid} update rulefirestore.rules · lines 72–81

  • It's just a fun toggle with no real stakes → delete the isPremium == resource.data.isPremium line from the update rule and let the client keep setting it directly, same as it does today.

Every rating carries a letter grade (LETTER_GRADE: 1→F … 10→A+), an emoji (EMOJI_BY_RATING), and a word label (LABEL_BY_RATING: "Terrible" … "Best Day Ever"). Notes & tags

An optional note (280 chars in the form, 600 stored) and up to 3 context tags from a fixed set of 12: Work, Sleep, Health, Social, Family, Love, Money, Weather, Travel, Hobby, News, Chores. ratedAtHour is only stamped on the first save of a given day, which is what lets the Early Bird / Night Owl citations key off "what time did you actually log this."

Privacy is two layers

A per-entry Private checkbox hides that specific day from friends regardless of anything else. Separately, the profile-level Share ratings / Share notes toggles in Settings control the default — a friend only ever sees a day if the entry isn't marked private and your profile-level sharing is on.

Features

Friends

Friendship is a single document per pair (friendships/{pairId}), state-machined through status. sendFriendRequest() looks the target up by usernameLower, then runs a transaction that reads the pair doc before writing — so a request can't be sent twice, and re-requesting an already-accepted pair or an already-pending one both fail cleanly with a specific message rather than a generic error.

TransitionWho can trigger itResult
Send requesteither user, via username searchstatus: 'pending'

Decline / canceleither side, while still pendingdoc hard-deleted (no messages exist yet)
Unfriendeither side, once acceptedstatus: 'ended' — soft-ended, not deleted, so chat history stays readable
Re-friendeither side, after endedsame doc flips back to 'pending' — old messages were never touched

Find People is an exact-username lookup (no fuzzy search) that shows a profile card with an Add button when you're not already friends or pending. The Notifications panel isn't its own collection — it's computed client-side each render from three arrays already in memory: incoming requests, friends with unread > 0, and outgoing (sent) requests.

Chat & voice notes

Chat is real-time via onSnapshot on friendships/{pairId}/messages, ordered by createdAt. There are exactly three message shapes, and all three are sent the same way — a batched write that both adds the message doc and bumps the friendship's lastMessageAt / lastMessageText / the recipient's unreadFor counter in one atomic batch.commit():

async function sendChatMessage(text) {

Sharing a day into chat

shareDayToChat() builds a day_share message from a past rating. It respects the sender's shareNotes setting at the moment of sharing — if notes are off, note is sent empty and noteHidden: true is set instead, so the recipient sees "note hidden" rather than nothing at all.

Voice notes

Recording uses MediaRecorder against a mono getUserMedia stream (echo cancellation, noise suppression, and auto-gain all requested), targeting audio/webm;codecs=opus at 32 kbps with fallbacks through ogg/mp4/plain webm/mpeg for browsers that don't support opus. Recording hard-stops at 30 seconds. On stop, the blob is base64-encoded and sent as a Firestore string field:

Reactions

Six quick-reaction emoji (❤️ 😂 😮 😢 👍 🔥). Reacting again with the same emoji removes it — toggled inside a transaction that only ever touches your own key in the reactions map, which is also exactly what the rule enforces (reactions.diff(...).affectedKeys().hasOnly([request.auth.uid])):

toggleReaction()index.html · lines 2619–2633
async function toggleReaction(pairId, messageId, emoji) {
  if (!pairId) return;
  const ref = db.collection('friendships').doc(pairId).collection('messages').doc(messageId);
  try {
    await db.runTransaction(async (tx) => {
      const snap = await tx.get(ref);
      if (!snap.exists) return;
      const reactions = snap.data().reactions || {};
      const mine = reactions[currentUser.uid];
      const updates = {};
      updates['reactions.' + currentUser.uid] = (mine === emoji) ? firebase.firestore.FieldValue.delete() : emoji;
      tx.update(ref, updates);
    });
  } catch (e) { /* non-fatal */ }
}
Features

Stats & compare

The Stats tab is entirely derived from your own ratings — no extra collection backs it. It computes a current streak and longest streak (consecutive logged days, gap-tolerant math via consecutiveDateRuns()), a calendar heatmap, a rating-bucket doughnut, a weekday breakdown (which day of the week tends to be your best/worst), and a trend line comparing recent averages to your all-time average.

The Compare tab runs the same math against one friend at a time (only over days that friend has chosen to share) and adds head-to-head framing: a "who's ahead this week" verdict, a win-streak banner, an agreement percentage — how often you're both within 1 point of each other on the same day — and four Chart.js visualizations (a shared line chart, a grouped bar chart of average/best day, and a doughnut per person).

Account deletion

Deletion requires typing your exact username plus your password (re-authenticated via the same fake-email credential trick from Authentication) before anything happens. Once confirmed, it's a soft delete of the data and a hard delete of the login:

  1. The users/{uid} doc is updated: deleted: true, displayName set to "Former Shitty Human", profileVisibility forced to 'public' (so the tombstone state is consistently visible rather than ambiguously hidden).
  2. The Firebase Auth user itself is deleted via currentUser.delete() — the login is genuinely gone.
  3. Ratings, past messages, and friendships are not purged — they stay in Firestore, just attached to a profile now marked deleted and rebranded.

Deployment

The app itself

It's a single static file, so GitHub Pages deployment is just: push index.html to the repo (the avatar image URLs already point at github.com/Jishnuec/shitty-human, so that's the natural home for it), then in the repo's Settings → Pages, point the Pages source at the branch/folder containing it. No build command, no output directory, no environment variables — the Firebase config is plain client-side data (see below), so there's nothing to inject at build time.

The rules

Deploy the Firestore rules with the Firebase CLI, from the same command already noted at the top of your rules file:

terminalfirebase-tools
firebase deploy --only firestore:rules

Resolve the isPremium conflict in Security rules before running this — deploying the rules as given, ahead of a code fix, is exactly what breaks the redeem button.

On the exposed API key

The Firebase web config (apiKey, authDomain, projectId, etc.) is hard-coded in index.html and visible to anyone who views source. That's expected and fine — Firebase's web API key identifies the project, it isn't a secret, and it's designed to be public. firestore.rules is the actual security boundary, which is exactly why the isPremium issue above is the finding that matters, not the config object sitting in plain sight next to it.
